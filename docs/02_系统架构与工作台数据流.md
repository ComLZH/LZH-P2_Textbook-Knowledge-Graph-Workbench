# 02. 系统架构与工作台数据流

更新时间：2026-09-13

## 1. 代码分层

| 层 | 目录/文件 | 职责 |
| --- | --- | --- |
| 契约 | `contracts.py`、`pipeline_contracts.py`、`review_document.py` | 来源、页面证据、局部线索、规范节点、v1 底稿、v2 聚合审查文档和正式图谱 DTO |
| Reader | `readers/`、`review_document_io.py`、`review_document_merge.py` | JSON、PDF、图片、v1/v2 审查包读取、基线校验和 Excel 三方合并 |
| Extractor | `extractors/`、`llm/` | 本地结构化抽取、旧候选协议、分阶段首轮抽取与关系整合 |
| Normalizer | `normalizers/`、`utils/` | 节点归一化、全部出现保留、别名映射、命名、关系、审核状态和旧层级兼容投影 |
| Exporter | `exporters/` | 工作底稿、正式图谱和 HTML 导出 |
| Quality/Mapping | `quality/`、`mapping/` | 建设态四维质量、旧图质量检查与正式分层映射 |
| Review View / Geometry | `review_views/`、`geometry/` | 关系/教材双投影、阅读顺序、关系分区、语义样式注册表、批量 ELK＋Python 混合布局、共享端口/路径/箭头/标签、G6 payload/HTML 与 Qt 适配输入 |
| Workbench Services | `services/` | 页面证据/OCR缓存、页序检查、章节清单、分阶段抽取、v2 审查会话、发布预检与原子正式发布 |
| Workflow | `workflows/`、`project_cli.py` | 命令行最小链路编排 |
| Desktop | `desktop_app.py` | 当前正式教师/教研桌面入口，负责界面状态、线程信号和交互 |

`desktop_app.py` 仍是当前正式教师入口；`web_app.py` 已在代码层复用 v2 会话、共享投影和发布预检，但当前环境缺少 FastAPI/Uvicorn，服务器版整体产品阶段仍以文档 15 为准。

2026-09-13 起，`WorkbenchReviewService.build_review_render_bundle()` 默认构造 `relations` 投影。投影额外携带 `ReadingSequence` 与 `VisualRelationGroup`；`layout_scene()` 在无 GUI/无 WebEngine 环境中批量调用随包 ELK，若运行时、结果或硬门禁失败则使用有界 Python 回退。G6 与 Qt 只负责绘制布局版本 6 的 `SceneGeometry`，不得重新计算业务端点、箭头或用直线替换失败路径。

## 2. 桌面工作台数据流

```text
选择教材文件与页码
-> WorkbenchAnalysisService
   -> SourceDocumentReader
   -> PageEvidenceService
      -> PDF 原生文本优先
      -> 扫描页共享 PaddleOCR 回退
      -> PageEvidenceBundleDTO 缓存
   -> 可选 PageContinuityChecker / 模型复核
   -> LlmStagedPageExtractor
      -> LocalNodeCandidateDTO
      -> LocalRelationClaimDTO
   -> NodeCanonicalizer / NodeAliasMappingDTO
   -> RelationClaimConsolidator
   -> 按章 LlmRelationCompletionService（仅文本证据）
   -> DraftKnowledgeItemDTO
   -> ReviewDocumentMigrator / P2ReviewDocumentDTO schema 2
      -> StructuralScopeDTO / KnowledgeOccurrenceDTO
      -> structure / membership / semantic / unresolved
-> ReviewDocumentSession(expected_revision)
   -> 原子编辑/审核/profile 命令
   -> 逻辑归档与追加历史撤销
   -> v2 审查包保存/打开/Excel 三方合并
-> ReviewProjectionBuilder
   -> 表示覆盖账本
   -> layout_scene 递归几何
   -> GraphReviewPayloadBuilder / G6ReviewHtmlRenderer
   -> Qt 兼容视图
-> 人工审核与修改
-> WorkbenchReviewService
   -> ReviewDocumentQualityChecker
   -> PublishPlanningService.preflight
   -> 显式 ExportProfile / 主归属选择
   -> FormalProjection（不读取画布状态）
   -> 暂存运行目录 + 文件哈希校验
   -> 原子提交运行 + current.json
```

## 3. 审核门禁

- 候选默认不等于正式节点。
- 正式图谱只接受满足导出条件的审核结果。
- 错误级质量问题阻止正式导出。
- 警告不一定阻止导出，但必须出现在质量报告中。
- 模型理由、证据文本、页码/图片位置和置信度用于审查，不替代教师确认。
- 候选 `contains` 在未通过时仍参与候选图嵌套；正确显示不等于正式接受。
- 结构批量确认同时处理结构节点和对应 `contains`，不接受其他语义关系。
- 已通过的结构子节点若缺少已通过父级，属于错误并阻止正式导出。

## 4. 本地与模型职责

- Reader 只读取和归一化来源，不判断最终知识关系。
- 本地规则负责确定性命名、枚举归一化、层级检查、关系强连通分量和章节内左向右分层。
- 大模型负责提供候选和结构建议，不直接写入正式图谱。
- 人工审查负责接受、拒绝、修订和专家复核判断。

分阶段链路中，图片主要感知一次。若本地 OCR 状态为 `ok`，首轮和最终关系阶段均使用缓存文本；只有 OCR 不可用、低质量或视觉区确实需要复核时，首轮才附带相关页面图片。最终关系阶段禁止新增节点。

页序检查默认关闭。开启后规则先检查文件页序、印刷页码、重复页面和文本边界；只有可疑相邻页才请求模型复核，任何结果都不会自动改变用户提供的页面顺序。

## 5. 整本书保护

- `BookManifestBuilder` 从缓存文本识别章节起止页、小节标题、目录/非正文页和印刷页码映射。
- 首轮抽取按最多 4 页或约 12000 字符分批。
- 每批模型临时节点 ID 会加本地批次命名空间，避免不同批次的 `n1` 相互覆盖。
- 节点先全局做保守归一化，再按章节进行关系补全；单个关系请求最多携带 80 个节点。
- 当前只提供结构和请求规模保护，尚未形成整册人工金标准与生产级准确率基线。

## 6. 当前架构限制

分析、审核导出、审查会话状态、撤销和主要编辑命令均已从桌面层拆出，第二阶段服务边界成立。桌面层仍保留表格控件同步、编辑对话框、Qt Graphics View 和 G6 WebView 双图谱渲染；下一阶段若继续工程拆分，应优先建立视图模型/表格适配器，再拆分渲染组件。

## 7. 层级事实与视图投影

分阶段首轮继续让节点和关系独立输出。关系归一化完成后，统一层级解析器读取 `contains` 和兼容父级字段，生成无歧义父子映射、冲突和结构深度。候选布局、G6 combo、正式工作簿和 `layer_mapping.json` 必须复用该结果，不能各自推断。

`container` 只是结构节点类型；`chapter`、`section`、`subsection` 是由父子映射和深度得到的结构角色。目录编号与页面顺序只影响排序，不直接生成强语义关系。

## 8. 双视图投影

- `GraphReviewPayloadBuilder` 把所有非 `contains` 正式候选关系放入 `edges`，不再因为端点是结构节点而隐藏。
- `contains` 只进入 `hierarchy`，供 G6 combo 与兼容视图章节框表达空间嵌套；底稿关系事实仍完整保留。
- `layout_edges` 是独立的低对比度辅助边，默认隐藏，不得替代或抑制真实关系。
- G6 `manual_positions` 是中心点坐标，仅由 G6 读写；兼容视图位置状态独立，默认由确定性章序布局计算。
- `utils/relation_layout.py` 输出章节内共享语义层级；G6 使用中心点坐标、兼容视图使用矩形坐标，但无环方向性边在两者中都遵循左向右，对称关系保持同层，循环回边保留真实语义。
- 节点/关系审查状态由两种视图共同读取；待修关系保持可见，只改变线型、透明度和标签。

## 9. 日期导出数据流

桌面端把用户选择目录视为导出根目录，实际调用 `WorkbenchReviewService` 时启用日期子目录：

```text
选择的导出根目录
-> YYYY-MM-DD/
   -> 清理上一轮已知产物
   -> reviewed_draft.xlsx
   -> graph_quality_report.md
   -> 质量通过：formal_graph.xlsx + layer_mapping.json
   -> export_manifest.json
```

命令行和服务调用为兼容既有用法，默认仍可直接写入传入目录；只有桌面正式导出默认启用日期子目录。导出清单记录来源、图谱 ID、质量计数、阻断原因和本轮真实文件集合。

以上是 v1 兼容导出路径。v2 正式发布不先清理当前目录，改为：

```text
P2ReviewDocumentDTO + ExportProfileDTO
-> 纯读取 PublishPlan
-> revision / 业务指纹 / profile 指纹 / 能力版本复核
-> .staging-<run_id>/
   -> formal_graph.xlsx
   -> layer_mapping.json
   -> publish_manifest.json + SHA-256
-> 提交 runs/<run_id>/
-> 原子替换 current.json
```

任何预检阻断都不创建正式输出；文件写入失败不删除上一有效运行。

## 10. 开发观测侧车

`progress_recording` 是分析和导出服务外的可选侧车：

```text
WorkbenchAnalysisRequest.progress_recording_mode
-> FileProgressRecorder / NullProgressRecorder
-> RecordingChatJsonClient(不改变 ChatJsonClient 契约)
-> OCR/模型/归一化/关系/布局/审查阶段产物
-> WorkbenchAnalysisResult.analysis_run_id
-> export_manifest.json + 08_export/export_manifest.json
```

记录器异常被隔离，不能改变业务返回值。`summary` 模式不保存提示词、原始响应和大型中间 DTO；`full` 模式才保存脱敏后详细产物。关系补全还额外输出逐章解析诊断，使模型原始输出与最终候选可直接对账。

## 11. v2 三条消费路径

```text
P2ReviewDocumentDTO
├─ DraftRowView / 桌面表格兼容快照 -> ReviewDocumentSession 命令
├─ ReviewViewProjection -> Recursive SceneGeometry -> G6 / Qt
└─ PublishPlan + FormalProjection -> P4 v1 正式表 / layer_mapping
```

- 视图中的 combo、卡片实例、坐标、折叠和筛选不是正式事实；多归属引用也不会复制业务节点。
- 正式投影只使用活动且已接受的显式关系，不调用旧 parent/prerequisite 推导补全。
- `view_state` 不推进业务 revision；节点、关系、归属和 profile 选择会推进 revision 并使旧发布计划失效。
- 旧 `WorkbenchReviewSession` 和旧日期导出继续服务历史调用；v2 入口失败时不回退到可能丢失多归属或未决语义的旧写入链路。

## 12. 布局版本 6 的共享场景数据流

```text
P2ReviewDocumentDTO
-> ReviewViewProjection
   -> 基础业务边 / 当前可见边
   -> ReadingSequence（证据绑定优先、上下文局部）
   -> VisualRelationGroup（基础图连通分量、稳定 ID）
-> 组件级布局候选
   -> 单进程 p2_elk_batch_v1 / Python 有界回退
   -> 有序 fanout 后处理（同列 Y 强制排序）
-> 组件作用域正交路由
   -> 节点障碍 / 稳定端口 / 终端直段 / 箭头多边形 / 标签矩形
-> 分区完整边界计算与二维打包
-> SceneLayoutResult v6 + GeometryMetrics v3
-> G6 自定义 path/arrow 与 Qt QPainterPath/QPolygonF
```

关键不变量：

- `routing_only` 只描述某条真实业务边不参加普通 rank 计算，不是布局辅助边，也不会被默认隐藏或从发布事实中移除。
- 分区框是派生的阅读几何，不进入知识对象、教材 scope、关系审核或 P4 正式导出。
- 有序步骤的 Y 坐标由共享后处理确定，两个渲染器不自行排序。
- 路由障碍和已占用线段按连通组件隔离；组件完成完整边界计算后再整体平移打包，平移必须同步更新节点、路径、箭头、标签与分区框。
- 总量大但组件均不超过 12 节点/24 边时允许完整布局；单个高密组件超出搜索预算时生成带失败边计数的诊断，不绘制未经验证的伪路径。
